# コードレビュー

通常のレビューで見逃される問題を発見するためのレビュー観点。PR / ファイル / 差分のいずれを見る場合も、シニアレビュアーとして、表面的な確認ではなくコードの意図と影響を理解した上で指摘する。

Issue / PR の書式は [gh-templates.md](gh-templates.md)、リポジトリ設定とブランチ衛生は [gh.md](gh.md) を参照する。

## 核心原則

まずコードを深く理解する。チェックリストを見る前に、コードが何をしているか完全に理解する。呼び出し元や設定ファイルなどの関連ファイルも確認する。理解が曖昧なまま指摘しない。

懸念点は全て報告する。少しでも気になった点は必ず報告する。「問題なし」と判断しても、検討した懸念点は参考情報として報告する。優先度が低くても報告し、最終判断は人間に委ねる。

深掘り質問で問題を掘り起こす。下記の質問を自分に問いかけて問題を発見する。「このコードは本当に正しいか」を常に疑う。

見落としやすいポイントを意識的に確認する。設定ファイル、環境変数、関連コードなど、通常のレビューで見落としがちな箇所を明示的に見る。

## 進め方

### レビュー対象を特定する

対象が明示されていない場合はユーザーに確認する。PR 番号または URL、ファイルパスまたはディレクトリ、ブランチの差分（例: 現在のブランチ vs main）のいずれか。対象が不明なままレビューを開始しない。

### コードを深く理解する

チェックリストを見る前に、以下を完了する。

- 対象コードを読み、何をしているか説明できるようにする
- 関連ファイルを特定して読む（このコードを呼び出している箇所、CI/CD や config や .env などの設定ファイル、関連するモジュール・サービス・型定義）
- データの流れを追う（入力 → 処理 → 出力）

この段階で以下を出力してから次に進む。工程を飛ばせないようにするための中間出力なので省略しない。

- このコードの目的を1〜2文で要約
- データの流れ
- 特定した関連ファイルのリスト
- この段階で気づいた懸念点

### 深掘り質問で問題を発見する

下記の「深掘り質問」を自分に問いかける。質問は Yes/No で確認する項目ではなく、問題を発見するための思考ツールとして使う。

避けたい使い方は「N+1問題がない」をチェックして OK とすること。望ましい使い方は「このクエリ、ループの中で呼ばれてない？関連データは事前にロードされてる？」と問いかけて調査し、問題を発見すること。

### 見落としやすいポイントを確認する

下記の「見落としやすいポイント」を確認する。

### 指摘を整理してレポートを作成する

発見した問題を優先度で分類し、下記の「レポートの構成」に従って出力する。

- Critical — セキュリティ、データ損失、本番障害の可能性
- High — バグ、パフォーマンス問題、設計上の問題
- Medium — 可読性、規約違反、改善の余地
- 参考情報 — 理論上の懸念だが実害は低いと判断したもの
- 確認事項 — 仕様や意図の確認が必要なもの

## レビュー対象ごとの追加確認

PR をレビューするときは `gh pr view <PR番号 or URL>` と `gh pr diff <PR番号 or URL>` で内容を取得する。PR 説明と実際の変更が一致しているか、変更の影響範囲が他のファイルに及んでいないかを追加で確認する。

ファイルやディレクトリをレビューするときは、対象ファイルを読み、関連ファイルも確認する。

差分をレビューするときは `git diff origin/main...HEAD` で取得する。変更箇所だけでなく、変更による影響範囲を追加で確認する。

## 見落としを防ぐ思考法

レビューの見落としは「変更の境界で止まる」ことで起きる。変更されたコードの外側を意識的に追跡しないと見落とす。

### 点ではなく線で見る

変更箇所（点）だけでなく、データや状態の流れ（線）を追う。状態を操作するコードを見つけたら、CRUD 全操作を検索して全体像を把握する。

- Create（作成）はどこ？
- Read（読み取り）はどこ？
- Update（更新）はどこ？条件付き更新（上書きしない）はある？
- Delete（削除）はどこ？

検索してヒットしないことは、その操作が存在しないことを意味する。これ自体が問題の可能性である。

このコードが扱う状態は何かを言語化する（localStorage、sessionStorage、Cookie、DB、キャッシュ、グローバル変数、シングルトンなど）。

### 今だけでなく時間軸で見る

現時点の動作だけでなく、時間経過を想像する。

- 初回は正しく動く。2回目は？10回目は？
- 1時間後は？1週間後は？
- 状態がリセットされないまま蓄積したらどうなる？

### 単体ではなく関係性で見る

この変更が他の機能とどう関係するかを確認する。

- 同じデータや状態を参照する他の機能はある？
- それぞれの機能が期待する動作は一致している？
- 一方の変更が他方に影響しないか？

## 深掘り質問

該当しないセクションはスキップする。

### セキュリティとデータ安全性

入力と出力。

- このユーザー入力、本当に信頼していい？エスケープは？
- SQL に直接値を埋め込んでいないか？プレースホルダ使ってる？
- HTML に出力するとき、エスケープされてる？生の HTML 出力を使ってない？
- ファイルパスにユーザー入力が含まれてない？パストラバーサルは？

認証と認可。

- この操作、誰でもできていい？認可チェックは？
- 他人のデータにアクセスできてしまわない？ID の検証は？

機密情報。

- API キー、パスワードがハードコードされてない？
- ログに機密情報を出力してない？

### ロジックと正確性

条件分岐。

- この条件、逆のケースは正しく処理される？
- 境界値（0、1、max）でどうなる？off-by-one エラーは？
- null や undefined が来たらどうなる？
- 空配列、空文字列のときは？

ループ。

- このループ、本当に終了する？無限ループの可能性は？
- ループ内でコレクションを変更してない？
- ループの中で DB / API 呼び出ししてない？（N+1）

状態管理。

- この変数、途中で予期せず変更されない？
- 非同期処理の完了を待ってる？レースコンディションは？
- トランザクション内で外部 API 呼んでない？（ロールバック不可）

データライフサイクル。「点ではなく線で見る」を適用する重要な領域。

- CRUD 全操作を検索したか？特に削除処理が存在しないケースに注意
- 「上書きしない」条件（`if (!exists)`）がある場合、古いデータが残り続けて問題ないか？
- このデータの寿命と、それを使う機能の寿命は一致しているか？
- キャッシュはいつ無効化される？古いデータが使われない？

エッジケース。

- 0件のとき何が起きる？
- 1件のときと複数件のときで動作が違わない？
- 最大件数を超えたらどうなる？

### パフォーマンス

データベース。

- このクエリ、ループの中で呼ばれてない？（N+1）
- 関連データは事前ロード（Eager Loading 等）されてる？
- インデックスは効く？`LIKE '%keyword'` のように `%` が先頭だとインデックスが効かない
- 全件取得してない？本当に全部必要？

メモリ。

- 大量データを一度にメモリに載せてない？
- chunk / cursor 処理が必要では？
- 巨大な配列をコピーしてない？

外部連携。

- タイムアウトは設定されてる？
- リトライ処理は？一時的なエラーで全体が失敗しない？
- レート制限に引っかからない？

### エラーハンドリング

例外処理。

- try-catch で例外を握りつぶしてない？
- エラー時、ユーザーに適切なメッセージが返る？
- エラーログは十分？原因特定できる情報がある？

失敗パターン。

- DB 接続が切れたらどうなる？
- 外部 API がタイムアウトしたら？
- ファイルが存在しなかったら？
- 権限がなかったら？

リカバリ。

- 途中で失敗したとき、中途半端な状態にならない？
- ロールバックは正しく動く？
- リトライしても安全？冪等性は？

### 設計と保守性

責任分担。

- この関数やクラス、やりすぎてない？（単一責任）
- ビジネスロジックがプレゼンテーション層に漏れてない？
- 同じようなコードが他にもない？（DRY）

依存関係。

- テストしにくい依存関係になってない？
- 循環依存してない？
- 依存方向は Interface → Application → Domain → Infrastructure の一方向を守れている？

可読性。

- この変数名、何を表してるか分かる？
- マジックナンバー使ってない？定数化すべきでは？
- ネストが深すぎない？早期リターンで改善できない？

### テスト

テストの存在。

- この変更に対するテストはある？追加が必要では？
- 既存テストが壊れてない？

テストの質。

- テストは実装の詳細ではなく振る舞いをテストしてる？
- エッジケース（境界値、空、null）のテストはある？
- テストの名前から何をテストしてるか分かる？

## 見落としやすいポイント

通常のレビューで見逃しがちな箇所。

関連ファイル。

- このコードを呼び出している他の箇所は？影響ない？
- 設定ファイル（buildspec、.env、config）に変更が必要では？
- 環境ごとに設定が違う場合、全環境で動く？

暗黙の前提。

- このコード、特定の順序で呼ばれる前提になってない？
- 初期化されている前提で使ってない？
- 特定の環境でしか動かない実装になってない？

並行処理。

- 同時に実行されたらどうなる？
- DB ロックは必要？デッドロックの可能性は？
- キューやバッチで並列実行されたとき大丈夫？

データ変更系。

- dry-run や確認機能はある？
- 失敗時のロールバックやリカバリ手段は？
- 影響範囲の制限（件数制限、WHERE 条件）は？

本番環境。

- 本番のデータ量で動く？パフォーマンスは？
- メモリ / ディスク / コネクションが枯渇しない？
- 既存データとの互換性は？マイグレーション必要？

## 報告の分類

指摘は実際に問題が発生しうるもの。バグ、セキュリティ、パフォーマンスなど。

参考情報は理論上の懸念だが実害は低いもの。「念のため確認したが問題なし」もここに書く。

確認事項は仕様や意図の確認が必要なもの。「これは意図的？」と問う。

懸念点を報告しないという選択肢はない。全て何らかの形で報告する。

## レポートの構成

冒頭に対象（ファイルパス / PR 番号 / ブランチ名）、レビュー日、レビュータイプを書く。

サマリー。Critical / High / Medium の件数を挙げ、結論（マージ可能 / 修正後マージ可能 / 要リワーク）を1〜2文の補足付きで明示する。良い点も書く。

指摘事項。Critical（即時対応が必要）、High（優先的に対応）、Medium（計画的に対応）の順に並べる。各項目に問題タイトル、場所（ファイル:行番号）、問題の具体的な説明を書く。Critical と High には修正前後のコード例を付ける。Medium は改善案の説明でよい。

参考情報。理論上の懸念点として、場所、懸念、なぜ優先度が低いと判断したかを書く。3件以上ある場合は箇条書きで簡潔にし、詳細説明は省く。

確認事項。仕様や意図の確認が必要な点をチェックボックスの箇条書きで並べる。

状態管理の検証。localStorage、sessionStorage、Cookie、DB、キャッシュ、グローバル変数などを扱うコードがある場合は必須。対象の状態を明記し、CRUD 各操作の検索結果（あり / なし、Update は条件付きか、それぞれの場所）を挙げる。「なし」は問題の可能性であり、特に Delete がない場合はデータが永続化されて問題ないかを確認する。あわせて時間軸シナリオ（初回操作、2回目操作、時間経過後のそれぞれで状態・期待値・実際）を検証し、同じ状態を参照する他の機能を列挙する（該当なしならそう書く）。

改善タスク。即時対応（Critical）、優先対応（High）、計画的に対応（Medium）に分けてチェックボックスで並べる。

## 完了条件

レポートを出す前に、本当に実行したか確認する。

- コードを深く理解した（説明できる状態）
- 関連ファイル（設定、呼び出し元）を確認した
- 深掘り質問を自分に問いかけた
- 見落としやすいポイントを確認した
- 全ての懸念点を報告した（参考情報を含む）
- 状態を扱うコードがあった場合、CRUD 全操作を検索した
- 「上書きしない」条件を見つけた場合、時間軸シナリオを検証した
- 同じ状態を参照する他の機能との関係を確認した
- 「〜の可能性がある」で止めず、具体的シナリオで確認した
- 問題の優先度を実際の影響度に基づいて判断した
- 結論（マージ可否）と次のアクションを明示した
